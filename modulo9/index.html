// PÍLULA 9.1 • ALFAIATARIA METODOLÓGICA

Você Não Precisa de Toda a Burocracia: O Tailoring

Um dos maiores erros de governança é aplicar o mesmo peso burocrático a todos os projetos. Exigir que um projeto de duas semanas preencha os mesmos relatórios de uma iniciativa estratégica bilionária é ineficiência operacional. O PMBOK resolve isso através do Tailoring (Alfaiataria): o GP extrai apenas os artefatos estritamente necessários ao nível de risco da entrega.

Desafio de Fixação: Gatilhos de Alfaiataria e Porte

🎯 PERGUNTA CRÍTICA DE TAILORING:
O PMO automatizou uma trava na planilha de demandas que classifica automaticamente qualquer projeto como "G" ou "GG" caso ele seja monitorado pelo Escritório de Transformação. Um GP assume um projeto dessa categoria e solicita a dispensa do cálculo de Valor Agregado (EVA), alegando que a entrega será rápida. Qual o posicionamento correto da governança?
[A] Dispensar o cálculo de EVA, visto que a velocidade de entrega indicada pelo GP anula as regras automáticas de porte definidas na planilha do PMO.
[B] Eliminar o projeto da planilha de demandas e instruir o time a trabalhar sem qualquer registro técnico de escopo ou prazos no PMO.
[C] Manter a exigência do cálculo de EVA de forma inegociável. Sendo um projeto classificado como G/GG pelo gatilho do Escritório de Transformação, a governança exige o monitoramento analítico de custos e tendências (CPI/SPI/EAC) para blindar o capital estratégico investido.
[D] Rebaixar o projeto para Pequeno Porte (P) manualmente para reduzir o volume de trabalho burocrático do GP durante o ciclo de sprints.
[E] Substituir o GP por um analista júnior e transferir a responsabilidade pelas linhas de base financeiras para o cliente final.

Desafio de Fixação: Matemática do Progresso Físico

🎯 PERGUNTA CRÍTICA DE MEDIÇÃO DE AVANÇO:
Um GP gerencia um projeto com 3 frentes de trabalho. Para calcular o progresso total, ele realiza uma média simples das porcentagens concluídas informadas pelo time técnico. Ao auditar os dados, o PMO constata que uma frente de alta complexidade (que consome 80% dos dias úteis totais) está atrasada, mas o relatório do GP aponta que o projeto está saudável. Onde está o erro metodológico?
[A] O GP errou ao não utilizar pontos de história subjetivos para estimar o progresso das tarefas operacionais diárias.
[B] O GP deveria suspender as entregas sucessivas e forçar o retorno ao modelo em cascata rígido, proibindo o fracionamento do escopo técnico.
[C] O comitê de governança deve aceitar o relatório do GP, assumindo que as variações de cálculos matemáticos de progresso são irrelevantes para a alta gerência.
[D] O time técnico deveria assumir a responsabilidade de atualizar as linhas de base financeiras diretamente no painel de lançamentos da controladoria corporativa.
[E] O erro está na aplicação da média simples. O progresso físico de tarefas complexas deve ser obrigatoriamente ponderado pelos dias úteis úteis de trabalho dedicados a cada pacote da EAP, garantindo que desvios em frentes pesadas distorçam o indicador global e gerem o alerta correto na controladoria.

Validação de Escopo e o Comitê de Mudanças (CCB)

O cliente quer mudar? O mercado mudou? Perfeito: nós acolhemos a evolução, mas avaliamos os impactos cruzados. Toda alteração precisa passar pelo rito formal de aprovação técnica e orçamentária do CCB antes de virar linha de código ou tarefa de campo.

O FLUXO DO CONTROLE INTEGRADO (CLIQUE PARA VER OS RITOS DE GOVERNANÇA):

01 // ANÁLISE DE IMPACTO

Quantificação prévia de custos adicionais (CR), impacto no Caminho Crítico e novos riscos de contrato.

EXPANDIR ANÁLISE 🔍

02 // RITO FORMAL (CCB)

Submissão ao comitê de mudanças. Se aprovada, repactua a Linha de Base; se rejeitada, blinda o escopo.

EXPANDIR RITO 🔍
// AVALIAÇÃO DE FIXAÇÃO • PÍLULA 9.3

Desafio de Fixação: A Falácia da Mudança "Pequena"

🎯 PERGUNTA CRÍTICA DE CONTROLE DE MUDANÇAS:
Durante a sprint de homologação de uma entrega sucessiva, o cliente exige uma alteração técnica de layout que, segundo o time operacional, levará apenas dois dias úteis para ser feita. O cliente afirma que por ser uma mudança pequena, não há necessidade de burocracias. Como o GP deve agir?
[A] Registrar a Solicitação de Mudança, avaliar o impacto técnico real nas linhas de base de custo, prazo e riscos, e submeter o pleito ao rito formal de aprovação do comitê de governança antes de autorizar o time a iniciar o trabalho.
[B] Executar a mudança imediatamente para demonstrar agilidade e evitar atritos comerciais com o cliente durante a sprint.
[C] Negar o pedido de forma agressiva, alegando que o PMBOK proíbe qualquer tipo de evolução ou refinamento estético após o desenho inicial da EAP.
[D] Solicitar que a controladoria desconte os custos dos dois dias úteis de trabalho diretamente do bônus de performance dos desenvolvedores do time.
[E] Abandonar o desenho da EAP original e transferir a propriedade de todas as linhas de base para o backlog pessoal do cliente.
